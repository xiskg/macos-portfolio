CasaOS MCP

Translating an AI tool protocol into application management across a real server boundary.

TypeScript · Node.js · MCP SDK · HTTP · SSH · Docker Compose

The problemArchitectureImplementationTrade-offsEvidence

Containers are only part of the model

Deploying a container does not automatically give CasaOS the metadata it needs for a native dashboard entry. The project bridges that gap by exposing application management through MCP and generating Compose configuration with x-casaos metadata.

The public repository credits João de Almeida (xiskg) in its README and MIT license. The engineering contribution is the server/client integration: tool definitions, protocol dispatch, remote operations and application metadata handling.

One protocol, several boundaries

AI client → MCP / stdio↓Tool schemas + request dispatch↓CasaOSClient → HTTP / SSH↓CasaOS metadata + Docker Compose

The MCP entry point declares the available tools and routes requests to CasaOSClient. The client combines HTTP reads with SSH operations. Keeping transport handling outside the tool registry makes the integration easier to inspect, even though further separation and validation would help.

Normalize what the server returns

The application inventory combines CasaOS grid data, Compose projects and container inspection. The returned object distinguishes native and legacy containers instead of presenting every source as the same thing.

    return {
      gridApps: gridData?.data || [],
      composeProjects: Object.keys(composeProjects),
      nativeApps,
      legacyContainers,
    };

Keep protocol errors recognizable

The request dispatcher maps caught errors into the MCP response shape using isError and text content. That demonstrates protocol-level error reporting, while leaving room for better validation and more structured error categories.

  } catch (error: any) {
    return {
      isError: true,
      content: [
        {
          type: 'text',
          text: `Error executing ${name}: ${error.message}`,
        },
      ],
    };
  }

A working bridge needs a trust boundary

Remote operations can change server state. The current implementation includes broad shell access and constructs shell commands from inputs. Tool schemas are useful descriptions, but the dispatcher also needs runtime validation, constrained operations and explicit authorization for writes.

Docker access is highly privileged even when the SSH account is not root. I would prioritize a read-only tool tier, bounded inputs and timeouts, safer command construction, audit records and redaction of logs and configuration output. These are defensive next steps, not completed security guarantees.

What the source supports

  • MCP tool registration and stdio transport are implemented.
  • HTTP/SSH integration and Compose metadata operations are visible in TypeScript source.
  • This case makes no claim of production hardening, independent security review or measured scale.
